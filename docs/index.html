How a change deleted from Git silently survives an Argo CD sync

Argo CD creates a Deployment with server-side apply. During an incident, someone changes it with kubectl: a CPU limit (demo-drift) or a re-created container (demo-container). Later Git deletes what was changed, Argo CD reports Synced, and the cluster keeps the change: Argo CD's diff hides the drift. Click through the timeline one change at a time. Three panels show the manifest in Git, the object in the cluster, and the field managers in metadata.managedFields. For Argo CD steps, the strip shows how Argo CD builds the desired state and applies it. All data is real API-server output from the test bed.

Based on How we scale deployments with a custom GitOps engine by Ramesh G. Iyer. The post attributes the loss of ownership to managedFields compaction. This test bed shows that ownership moves earlier, when kubectl changes the value; compaction then hides who owns the field (demo-compacted).
